# Community puzzle workflow

The application keeps the existing three game IDs and engines: `player` = **Player Guess**, `ladder` = **Stat Ladder**, and `cross` = **CrossSport**. No game was renamed or reformatted.

Friends use `create/`; owners sign in at `admin.html` and review at `admin/submissions/`. The intended path is **create → preview → submit → owner edit/approve → copy game JSON → choose/load date → import one game → publish the complete slate**. Approval and import into a draft do not publish a puzzle.

## One-game JSON contract

Every regular import/export is an object with:

| Field | Meaning |
| --- | --- |
| `schemaVersion` | Integer `1` |
| `game` | Exactly `player`, `ladder`, or `cross` |
| `creatorCredit` | Optional public name, or an empty string for no credit |
| `submissionId` | Optional source ID, included by approved review exports |
| `data` | The selected game's existing engine data, described below |

The owner selects the date separately. Game JSON cannot select another date or contain the other two games. Files must be smaller than 60 KB; game data must be smaller than 50 KB. The full dated slate retains its existing 60 KB validation limit.

### Player Guess

`data` contains `answer` (1–120 characters), `sport` (1–30), `aliases` (up to 20 accepted strings, each 1–120), and `hints` (exactly five nonempty strings, each at most 500 characters). Clue order determines points, from 5 down to 1. Start with a distinctive stat or career fact, then add useful context. The form supports editing, removing/adding up to five clues, and moving them up/down.

Valid example: [examples/player.json](examples/player.json).

### Stat Ladder

`data.questions` contains exactly five question objects in easy-to-hard order. Each has `question` (1–500 characters), `answer` (1–120), `sport` (1–30), `aliases` (up to 20 strings), and `source` (an HTTPS URL). The existing one-guess and 1–5 point weighting rules remain unchanged.

Valid example: [examples/ladder.json](examples/ladder.json).

### CrossSport

`data` contains integer `size` from 5 to 11 and `entries` with 2–40 words. Each entry has `answer`, `clue`, zero-based `row` and `col`, and `direction` (`across` or `down`). The form uses one-based coordinates for people and converts them automatically. The existing crossword validator checks bounds, matching intersections, no same-direction overlaps, connectivity, both directions, and a clue for every contiguous run. Numbering is generated by the engine.

Valid example: [examples/cross.json](examples/cross.json).

## Safe date imports

`dailyPuzzles/{YYYY-MM-DD}` is retained. Its `puzzle` map still holds `schemaVersion`, `date`, `title`, `playerGuess`, `statLadder`, and `crossSport`. A new private draft may temporarily contain only imported game fields. The public loader only accepts complete, published, released slates.

An import transaction checks the loaded revision and release lock, then updates only `puzzle.playerGuess`, `puzzle.statLadder`, or `puzzle.crossSport`, plus that game's credit and the revision metadata. It preserves the other game fields and the publication state. New dates begin as private drafts. Existing slots require a confirmation naming the game and date. A newer revision invalidates an earlier confirmation, so a second editor cannot silently replace unseen changes.

The normal bulk editor can still save a complete day, but the one-game importer never replaces the full `puzzle` map. Unsaved working-copy edits to other games are retained locally and aren't included in that import transaction. Importing three games in sequence fills the same dated document; publishing requires all three to validate.

Existing published slates and results need no migration. Legacy whole-slate JSON backups are deliberately rejected by the regular one-game importer; export a selected game from the existing owner editor instead.

## Creator credits

The dated document has an optional root `credits` map, keyed by `player`, `ladder`, and `cross`. Each entry contains `displayName` and an optional `submissionId`. Keeping it outside `puzzle` lets rules permit owner-only credit corrections while refusing changes to released answers, clues, release settings, or publication state.

Names use 2–24 ASCII letters, numbers, spaces, dots, underscores, or hyphens, starting with a letter or number and without surrounding spaces. Forms validate them and game views render them as text. Original proposed names never travel in the exported game JSON. A blank owner credit hides the public attribution.

The game header and completion panel show **Submitted by NAME**. Review saves can correct linked public credits after publication while leaving the puzzle content unchanged. The owner desk also has **Save creator names only**. Linked review records retain the original submitted name and content.

## Firestore collections and permissions

| Collection | Contents and access |
| --- | --- |
| `submissions/{random ID}` | Original game, proposed name, canonical `puzzleJson`, player UID, server creation time, status, and revision. Anonymous or registered players can create a bounded `pending` record through the paired transaction. Only owners can read/list or review it. |
| `submissionLimits/{UID}` | Server-timed rolling 24-hour window, count, last submission time, and matching submission ID. A player can read their own limit but can change it only as part of a valid paired new submission. No client deletes. |
| `dailyPuzzles/{date}` | Existing daily document, with optional credits and partial private draft support. Public reads still require published + released. Only owners can change schedules or game data. |

Review fields are `reviewedName`, `reviewedPuzzleJson`, `reviewedBy`, `reviewedAt`, `revision`, and `status`. Publication records add `publishedDates` and `publishedAt`. Reviews cannot rewrite the original proposed name, original JSON, submitter, game type, or creation timestamp. Owner approval performs the complete engine validation before export; bounded original JSON remains private even if a malicious client bypasses form validation. Invalid originals can be rejected without parsing them.

Publication is still controlled by the owner desk. Successfully publishing/scheduling a credited slate marks linked approved suggestions **Published** and records the assigned date. Subsequent reviewed puzzle-content edits change the export; importing those edits remains a separate confirmed action. Released game content stays locked.

## Spam protection and cost

Submission and limit updates are atomic. Rules use `getAfter()` to require both writes, enforce at least 60 seconds between suggestions, and permit at most five suggestions per rolling 24 hours per Firebase identity. The public form also has a honeypot, field lengths, full game validation, and useful saved-draft error handling. These are per-identity limits, not IP limits.

The review page loads 50 suggestions at a time, newest first, using the automatic creation-time index. Game/status filters apply to loaded suggestions; **Load older submissions** adds earlier pages. No composite index, Cloud Function, paid email service, storage bucket, or billing upgrade is required. Everything continues on GitHub Pages and Firebase Spark.

2. Deploy the static build through the existing GitHub Actions workflow. The allowlist includes `create/index.html`, `admin/submissions/index.html`, and the shared scripts/styles. Asset revisions include both nested pages.
